## 重要发现：联机 mod 的 _ready 断链问题

**SteamCouchCoop**（当前最热门的第三方联机 mod）扩展了 `coop_shop.gd`，其 `_ready()` **不调用父类**。AGiftforMyFosterSon 原设计在 base_shop 扩展的 `_ready` 里连接赠送信号——在联机 mod 激活时这个 `_ready` 会被跳过，导致**赠送按钮可见但点击无响应**。

**v0.1.2 修复**：`_on_GiftButton_pressed` 现在双通道派发——
1. 信号有监听者 → 走原信号路径（本地合作）
2. 信号无人监听 → 向上遍历节点树找到商店节点，直接调用 `_on_item_gift_button_pressed`（该方法在脚本继承链上永远存在，不受任何 mod 的 `_ready` 断链影响）

该机制对所有"不调用父类 `_ready`"的 mod 通用兜底，不限于联机 mod。

## 审计中记录的其他模式

- 本轮榜单确认：1.2 生态的 UI mod 作者普遍遵守"先调父类"惯例（skadi、InfiniteMaterials 的 `_update` 类方法都规范调用父类），GML 同脚本多扩展链接是安全的
- 没有任何热门 mod 覆盖 `RunData.remove_item` / `add_item` / `get_player_items`——AGiftforMyFosterSon 的转移核心路径无外部竞争
- ItemRefund 证明了 1.2 时代"动态挂钩 + 不做脚本扩展"的新潮流（比 script extension 更新潮、天然低冲突）；AGiftforMyFosterSon 的弹窗侧未来可考虑迁移到此模式以彻底消除同脚本扩展冲突（v2 候选）
